# ovh_email_domain_dkim

Enables DKIM signing on an OVHcloud MX Plan email domain. Destroying the resource disables DKIM again.

OVHcloud allocates two selectors per domain and rotates the active one. Their CNAME records must be published in the
DNS zone before signing can start. When the zone is hosted by OVHcloud this happens automatically and `autoconfig` is
`true`. When it is hosted elsewhere, `autoconfig` is `false` and the records have to be created explicitly, which the
`selectors` attribute is there to feed.

## Example Usage

```terraform
resource "ovh_email_domain_dkim" "my_dkim" {
  domain = "example.com"
}
```

With the DNS zone hosted elsewhere, Cloudflare here, the `selectors` attribute feeds the records to publish:

```terraform
resource "ovh_email_domain_dkim" "my_dkim" {
  domain = "example.com"
}

# The selectors are only known once DKIM is enabled, and for_each needs its keys
# at plan time. OVHcloud allocates exactly two and the list is sorted, so a fixed
# count works on the first apply too.
resource "cloudflare_dns_record" "dkim_selectors" {
  count = 2

  zone_id = var.cloudflare_zone_id
  name    = "${ovh_email_domain_dkim.my_dkim.selectors[count.index].selector_name}._domainkey.example.com"
  type    = "CNAME"
  ttl     = 1
  proxied = false

  # cname is a full zone-file line, the target is its last field
  content = reverse(split(" ", ovh_email_domain_dkim.my_dkim.selectors[count.index].cname))[0]
}
```

A zone hosted by OVHcloud needs none of this: OVHcloud publishes the selectors itself.

## Notes

The domain has to be on an MX Plan offer. Zimbra, Email Pro and Exchange domains have DKIM APIs of their own, and a
redirect-only offer has none, which the API does not signal usefully: `PUT .../dkim/enable` returns `200`, no selector is
ever allocated, and the status stays `disabled`. The resource surfaces that as an activation timeout after two minutes
rather than reporting a success that never happened.

Enabling DKIM is asynchronous. The resource polls until the status settles, capped at two minutes. Both `modifying` and
`disabled` are treated as transient during activation: once the enable is accepted, the API can keep answering `disabled`
for several seconds before it flips to `enabled`.

Disabling is asynchronous too, so destroying the resource polls until the status reads `disabled`, capped at five
minutes. A replacement therefore never calls enable while the disable is still under way.

A successful apply does not by itself mean messages are being signed. If the selector records are not published yet, the
status settles on `toConfigure` and the resource emits a warning rather than an error, since publishing them is a
separate step and may well live in another provider's configuration.

Creating the resource for a domain that already has DKIM on fails with a `409`, pointing at `terraform import`. An
activation that fails or times out after the enable call was accepted leaves the resource tainted instead, so the next
apply disables and re-enables DKIM rather than meeting that `409`. Disabling DKIM outside Terraform removes the resource
from state on the next refresh, so a subsequent apply re-enables it.

`selectors` is sorted by `selector_name`. The API returns the list in no particular order and has been observed swapping
two selectors between consecutive calls, which would otherwise churn this attribute on every refresh.

## Import

DKIM configuration can be imported using its `domain`:

```bash
terraform import ovh_email_domain_dkim.my_dkim example.com
```
